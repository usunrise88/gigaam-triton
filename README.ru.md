# gigaam-triton

[English](README.md) · **Русский**

Инференс русской ASR-модели [GigaAM v3](https://github.com/salute-developers/GigaAM) на
NVIDIA Triton Inference Server: TensorRT на Blackwell (SM120) и ONNX Runtime на CPU.

- Все четыре варианта v3: `v3_e2e_ctc`, `v3_e2e_rnnt`, `v3_ctc`, `v3_rnnt`.
- Три рантайма: TensorRT, ONNX Runtime на GPU и ONNX Runtime на CPU с динамическим int8.
- Вход одинаковый для всех вариантов и рантаймов: сырые сэмплы float32 16 кГц. На выходе
  текст, токены и оценки по токенам, а у CTC-вариантов ещё и полные логарифмические
  вероятности, чтобы клиент мог декодировать сам.
- В runtime-образе нет torch. Признаки считаются на numpy, и эта реализация обязана совпасть
  с torchaudio, иначе сборка не проходит.
- Плохой вход падает громко. Сама модель на int16-масштабе молча возвращает пустую строку,
  поэтому сервер явно проверяет dtype и диапазон и возвращает ошибку.

## 1. Что нужно на хосте

Всё тяжёлое работает в контейнерах. На самой машине нужно только это:

| Требование | Проверка |
|---|---|
| GPU NVIDIA + драйвер | `nvidia-smi` |
| Docker ≥ 24 | `docker --version` |
| NVIDIA Container Toolkit | `docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi` |
| Python 3.8+ (только стандартная библиотека) | `python3 --version` |
| ~60 ГБ свободного места | `df -h /` |
| Доступ в интернет | образы NVIDIA NGC, PyPI, CDN с весами GigaAM |

**Для сборки pip-пакеты на хосте не нужны**: `build.sh` и `scripts/detect_env.py` обходятся
стандартной библиотекой. Исключение одно — модуль оценки качества (см. [§7](#7-оценка-качества)).

Место на диске: базовый образ Triton занимает ~31 ГБ, builder ~44 ГБ, runtime ~35 ГБ (слои
общие, так что на деле меньше). ONNX-экспорты — ~2 ГБ, TRT-движок — ~0.8 ГБ на вариант.
Если места не хватает, `docker builder prune` обычно освобождает десятки гигабайт.

## 2. Быстрый старт

```bash
git clone https://github.com/usunrise88/gigaam-triton.git && cd gigaam-triton
./build.sh --variant v3_e2e_ctc --runtime trt --precision fp16 \
           --buckets 2,5,10,20 --verify
```

Первый прогон делает всё:

1. находит базовый образ, который работает на этом GPU;
2. собирает builder-образ;
3. сверяет фронтенд с torchaudio;
4. качает веса (~1.7 ГБ, кэшируются в `~/.cache/gigaam`);
5. экспортирует ONNX и собирает TensorRT-движок;
6. собирает runtime-образ.

С `--verify` он в конце поднимает сервер и гоняет smoke-тест.

**Это занимает около часа**, из них ~40 минут уходит на сборку TensorRT-движка. Повторные
запуски идемпотентны: артефакты с валидным ключом кэша не пересобираются.

Затем запустите сервер:

```bash
docker run -d --gpus all --name gigaam-triton \
  -p 18000:18000 -p 18001:18001 -p 18002:18002 \
  -v "$PWD/cache:/cache" \
  -e VARIANT=v3_e2e_ctc -e RUNTIME=trt -e PRECISION=fp16 \
  gigaam-triton:0.1

curl -sf http://localhost:18000/v2/health/ready && echo ready
```

Порты 18000/18001/18002 — это HTTP, gRPC и метрики. Как работать с сервером из клиента,
описано в [`INTEGRATION.md`](INTEGRATION.md).

Если запустить контейнер с другими `BUCKETS` или `PRECISION`, entrypoint заметит, что движок
не подходит, и пересоберёт его при старте. На это нужно заложить время.

## 3. Параметры сборки

| Флаг | Значения | По умолчанию |
|---|---|---|
| `--variant` | `v3_e2e_ctc`, `v3_e2e_rnnt`, `v3_ctc`, `v3_rnnt`; можно списком через запятую | `v3_e2e_ctc` |
| `--runtime` | `trt`, `onnx-gpu`, `onnx-cpu` | `trt` |
| `--precision` | `fp16`, `bf16`, `fp32`, `int8` (только с `onnx-cpu`) | `fp16` на GPU, `int8` на CPU |
| `--buckets` | границы длительности в секундах через запятую или `none` | `2,5,10,20` |
| `--max-batch-size` | | `8` |
| `--instances` | число инстансов энкодера на GPU | `2` |
| `--cpu-instances` / `--intra-op-threads` | CPU-профиль | `6` / `4` |
| `--image` / `--model-repo` / `--cache` | тег образа и пути | `gigaam-triton:0.1`, `./model_repo`, `./cache` |
| `--skip-trt` | собрать движок при первом старте контейнера, а не сейчас | выкл. |
| `--verify` | поднять сервер и прогнать smoke-тест | выкл. |
| `--force` | пересобрать всё, игнорируя кэш | выкл. |
| `--pull` | разрешить скачивать кандидатные базовые образы (~30 ГБ каждый) | выкл. |

### Шаги сборки

1. **Окружение.** `detect_env.py` читает `nvidia-smi`, перебирает кандидатные образы Triton и
   для каждого **реально собирает пробный движок** под найденную compute capability. Первый
   прошедший образ записывается в `cache/env.json`. Версия образа нигде не захардкожена:
   инструкция апстрима фиксирует TensorRT, который старше поддержки SM120, и на Blackwell он
   либо падает, либо молча уходит в медленный JIT. Если не прошёл ни один кандидат, скрипт
   останавливается и выводит список проверенного. Молча откатываться на CPU он **не** станет.
2. **Builder-образ:** torch, `gigaam` и инструменты ONNX. Наружу не отгружается.
3. **Гейт log-mel.** В runtime нет torch, поэтому фронтенд пересчитывается на numpy по
   фильтрбанку, экспортированному из torchaudio. Гейт сверяет обе реализации с
   float64-референсом, и при расхождении сборка падает. Иначе тихое расхождение
   проявится просадкой WER, причину которой потом будут искать в модели.
4. **Экспорт ONNX** с проверкой против torch на golden-наборе (порог CER 0.5 %).
5. **TensorRT-движок:** один `.plan`, по оптимизационному профилю на каждый бакет длительности.
6. **Runtime-образ:** тонкий, без torch и без пакета `gigaam`.

Артефакты кладутся в `artifacts/<precision>/`, движки и отчёты — в `cache/`.

## 4. Проверка и замеры

```bash
# Юнит-проверки бэкендов: CTC collapse, токенизатор, log-mel
docker run --rm -v "$PWD/artifacts/fp16:/work/onnx" gigaam-triton-builder:0.1 \
  python3 scripts/test_backends.py --onnx-root /work/onnx --variant v3_e2e_ctc

# Сквозной smoke-тест против запущенного сервера
docker exec gigaam-triton python3 /opt/gigaam/scripts/smoke_test.py \
  --url localhost:18001 --repo /models --golden-dir /testdata/golden

# Матрица задержки и пропускной способности
docker exec gigaam-triton python3 /opt/gigaam/scripts/perf_profile.py \
  --url localhost:18001 --repo /models --out /cache/perf/report.json

# Сводная таблица по всем накопленным отчётам
python3 scripts/perf_summary.py
```

Smoke-тест проверяет три вещи, которых успешная сборка не гарантирует:

- прогревает ensemble (сам Triton этого не умеет);
- сверяет транскрипт с эталоном из torch;
- проверяет, что **плохой вход падает громко**: int16-масштаб, NaN, битая длина.

Эти переменные рантайма лучше подобрать под свою нагрузку, чем оставлять по умолчанию:

| Переменная | По умолчанию | Комментарий |
|---|---|---|
| `INSTANCES` | `2` | По нашим замерам второй инстанс энкодера окупается только от ~32 одновременных запросов. |
| `MAX_QUEUE_DELAY_US` | `1000` | При одном клиентском потоке это чистая задержка, которая платится на каждом шаге ensemble. |
| `WARMUP_COUNT` | `3` | Прогрев на CPU может занимать минуты. |

## 5. CPU-профиль

```bash
./build.sh --variant v3_e2e_ctc --runtime onnx-cpu --precision int8
```

Квантизация динамическая, калибровочный набор не нужен. Скрипт сам определяет возможности
CPU и печатает качество до и после квантизации: цифра скорости без цифры качества ничего не
значит.

Две оговорки:

- **Без VNNI int8 не ускоряет вообще.** Выигрыш только в размере графа (886 → 321 МБ).
  `reduce_range` выбирается по флагам CPU: если на процессоре без VNNI его выключить,
  аккумулятор насыщается и качество падает.
- **Прогрев стоит `инстансы × бакеты × count`.** Шесть инстансов могут греться минутами,
  поэтому для CPU-деплоя уменьшайте `WARMUP_COUNT`.

## 6. RNNT

```bash
./build.sh --variant v3_e2e_rnnt --runtime trt --precision fp16
docker run -d --gpus all ... -e VARIANT=v3_e2e_rnnt -e RNNT_PROVIDER=cpu ...
```

Цикл транспьюсера — известное узкое место: здесь он занимает 64–80 % времени запроса. Все
буферы преаллоцированы, состояние LSTM не ходит через хост. Вход джойнта берётся смещением
указателя, без копий на каждый кадр.

`RNNT_PROVIDER=cpu` стоит по умолчанию по результату замера: на CPU цикл в 1.5 раза быстрее,
чем на CUDA. На матрицах такого размера запуск ядра и синхронизация дороже самой арифметики.

На GPU CTC-вариант быстрее во всех измеренных точках. RNNT имеет смысл брать, только если его
точность важнее задержки.

## 7. Оценка качества

Это единственная часть, которой нужны Python-пакеты на хосте:

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install numpy scipy soundfile 'tritonclient[grpc]' num2words
pip install git+https://github.com/voicekit-team/T-one.git   # только для сравнения с T-one
```

Запуск:

```bash
docker cp gigaam-triton:/models/manifest.json /tmp/manifest.json
python eval/run_eval.py --audio-dir eval/audio \
  --gigaam-manifest /tmp/manifest.json --skip-tone
```

Аудио кладётся в `eval/audio/` парами: `имя.wav` и эталонный транскрипт `имя.txt`. Самих
аудиофайлов в репозитории нет.

Если сравниваете с другой ASR-системой:

- **Прогоняйте конкурента его собственным официальным клиентом**, а не своей реализацией его
  декодера. Иначе вы измеряете свою реконструкцию, а не систему.
- **Эталоны не должны быть порождены ни одной из сравниваемых систем.** Если эталон скопирован
  из вывода одной из систем, она получает на нём нулевую ошибку по построению.

`eval/normalize.py` приводит обе стороны к устной форме: нижний регистр, `ё` → `е`, без
пунктуации, числа словами. Самотесты встроены: `python eval/normalize.py`.

```

docker/
  Dockerfile.builder      torch + gigaam + TensorRT; тяжёлый, не отгружается
  Dockerfile.runtime      тонкий: без torch, без gigaam
  entrypoint.sh           проверка движка -> генерация model repository -> tritonserver

  detect_env.py           проба GPU, выбор базового образа -> cache/env.json
  export_onnx.py          PyTorch -> ONNX, meta.json, фильтрбанк, golden-проверка
  check_logmel.py         гейт: numpy log-mel обязан совпасть с torchaudio
  quantize_onnx.py        динамический int8 + качество до и после
  buckets.py              общая таблица бакетов, чтобы формы не разъезжались
  build_trt.py            ONNX -> TensorRT, профиль на бакет, ключ кэша
  gen_model_repo.py       генерация model repository
  smoke_test.py           сквозной тест + негативные проверки
  perf_profile.py         матрица задержки
  perf_summary.py         сводная таблица по отчётам
  test_backends.py        юнит-проверки бэкендов
backends/                 Python-бэкенды Triton (без torch)
templates/config/         шаблоны config.pbtxt
eval/                     нормализация, обёртки движков, прогон сравнения
testdata/golden/          эталонные транскрипты для smoke-теста
artifacts/<precision>/    результат экспорта (в .gitignore)
cache/                    env.json, движки, timing cache, отчёты (движки в .gitignore)
```

## 9. Что стоит знать заранее

**Не начинайте с апстримового `triton_scripts/`.** Его конвертер заменяет логпробы CTC на
`argmax` и выбрасывает ровно тот выход, который нужен клиенту для собственного
декодирования. Здесь отдаётся и то, и другое: логпробы — клиенту, а argmax считается на GPU,
чтобы Python-бэкенд оставался дешёвым.

**Препроцессинг v3 отличается от дефолтов библиотеки.** У v3 `n_fft=320` и `center=False`, у
v2 — 400 с центрированием. Все счётчики кадров выводятся из `meta.json`, а не предполагаются.
Смешивать v2 и v3 в одном model repository запрещено отдельной проверкой.

**Голова CTC на один класс шире токенизатора:** 256 токенов, 257 классов, blank на индексе
256. `vocab_size` и `num_classes` — разные поля не случайно.

**`ffmpeg` — необъявленная зависимость `gigaam`.** В образе Triton его нет, поэтому оба
Dockerfile его ставят.

**Движки привязаны к машине.** GPU, драйвер, версия TensorRT и флаги сборки входят в ключ
кэша, так что после обновления драйвера `.plan` перестаёт подходить. Это ловится
автоматически, но время на пересборку при деплое нужно заложить.

**Дефолты, выставленные по замерам** (менять только после нового замера):

- Пулы потоков numpy прибиты к одному потоку. На маленьких массивах пул дороже самой работы;
  это ускорило препроцессинг в 3 раза.
- CUDA-графы выключены. Выигрыша не нашлось, а захват на части инстансов падает.
- Цикл RNNT работает на CPU (см. [§6](#6-rnnt)).
