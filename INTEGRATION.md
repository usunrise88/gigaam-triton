# Спецификация интеграции `gigaam-triton` как ASR/STT

Версия 0.1 · для подключения из стороннего проекта.

Описывает **контракт сервиса**, а не его внутреннее устройство. Всё, что здесь
написано, проверено на работающем сервере; числа помечены условиями замера.
Как собрать сам сервис — `README.md`, что и почему устроено именно так —
`PREP.md` и `gigaam-triton-spec.md`.

---

## 1. Что это

Triton Inference Server, обслуживающий русскую ASR-модель GigaAM v3. Общается по
gRPC и HTTP, принимает сырые сэмплы, отдаёт текст и, для CTC-варианта, полные
логарифмические вероятности для собственного декодирования на стороне клиента.

Варианты моделей:

| Вариант | Выход | Когда брать |
|---|---|---|
| `v3_e2e_ctc` | cased, пунктуация, числа цифрами | **дефолт**, быстрее всех |
| `v3_e2e_rnnt` | cased, пунктуация | если качество важнее задержки, см. §8 |
| `v3_ctc` | lowercase, без пунктуации | сравнение с системами такого же таргета |
| `v3_rnnt` | lowercase, без пунктуации | то же |

### Чего сервис не делает

- **Не потоковый.** Энкодер полноконтекстный, состояния между вызовами нет.
  Подавать чанками по 300 мс, как это делают стриминговые ASR, нельзя — это
  архитектурное ограничение модели, а не настройка. См. §4.
- **Не диаризует и не детектирует речь.** VAD и разбиение на сегменты — на
  стороне клиента.
- **Не ресемплит.** Ожидает ровно 16 кГц, см. §3.

## 2. Развёртывание

```bash
docker run -d --gpus all --name gigaam-triton \
  -p 18000:18000 -p 18001:18001 -p 18002:18002 \
  -v /var/lib/gigaam-cache:/cache \
  -e VARIANT=v3_e2e_ctc \
  -e RUNTIME=trt \
  -e PRECISION=fp16 \
  -e BUCKETS=3 \
  -e INSTANCES=1 \
  gigaam-triton:0.1
```

Набор бакетов и число инстансов выше — не универсальный дефолт, а подобранная
конфигурация: один бакет на 3 секунды и один инстанс. Обоснование в §4 и §8,
образ по умолчанию собран под `2,5,10,20` и два инстанса.

| Порт | Назначение |
|---|---|
| 18000 | HTTP, в т.ч. `/v2/health/ready` |
| 18001 | gRPC — рабочий интерфейс |
| 18002 | Prometheus-метрики |

Порты не 8000-е намеренно: на машине, где сервис разрабатывался, 17000-е заняты
другим Triton. Меняются через `-p`, внутри контейнера они фиксированы.

### Переменные окружения

| Переменная | Дефолт | Смысл |
|---|---|---|
| `VARIANT` | `v3_e2e_ctc` | вариант модели из §1 |
| `RUNTIME` | `trt` | `trt`, `onnx-gpu`, `onnx-cpu` |
| `PRECISION` | `fp16` | `fp16`, `bf16`, `fp32`; `int8` только для `onnx-cpu` |
| `BUCKETS` | `2,5,10,20` | границы бакетов в секундах, см. §4. Смена набора требует пересборки движка (~10 мин) |
| `MAX_BATCH_SIZE` | `8` | потолок динамического батчинга |
| `INSTANCES` | `2` | инстансов энкодера на GPU |
| `CPU_INSTANCES` / `INTRA_OP_THREADS` | `6` / `4` | CPU-профиль; произведение ≈ числу ядер |
| `WARMUP_COUNT` | `3` | прогревов на бакет; на CPU уменьшать |
| `CUDA_GRAPHS` | `auto` | `auto` = выключено, замером выигрыша не найдено |
| `MAX_QUEUE_DELAY_US` | `1000` | сколько ждать сборки батча. При одиночном потоке это чистая задержка, платится на каждом шаге ансамбля — см. §8 |
| `RNNT_PROVIDER` | `cpu` | где крутить цикл транспьюсера; `cpu` быстрее в 1.5 раза |

**Том `/cache` обязателен и должен переживать перезапуски.** В нём лежит
TensorRT-движок, привязанный к конкретному GPU, драйверу и версии TRT. При
первом старте он собирается — это **минуты, а не секунды** (на RTX PRO 5000
Blackwell 4 бакета собирались 38 минут вхолодную и 14 минут при готовом
timing cache). При совпадении ключа кэша старт занимает ~33 с.

Обновление драйвера NVIDIA или образа делает движок нерабочим. Сервис это
обнаруживает по ключу кэша и пересобирает, сообщая в лог, что именно изменилось.
**Закладывайте это время в процедуру деплоя.**

### Готовность

`GET :18000/v2/health/ready` → 200. До этого момента сервер не отвечает на
инференс. Ждать надо с запасом на сборку движка (см. выше), а не по
фиксированному таймауту в 30 с.

## 3. Требования к аудио

| Параметр | Значение |
|---|---|
| Частота | **ровно 16000 Гц** |
| Каналы | моно |
| Формат | `float32` в диапазоне **[-1, 1]** |
| Длительность сегмента | ≤ размера наибольшего бакета (потолок модели 25 с) |

**Конвертировать, а не приводить типы.** Если подать int16-сэмплы, механически
переложенные в float32 (значения порядка тысяч), сервис вернёт **явную ошибку**.
Это сделано специально: сама модель в таком случае молча отдаёт пустую строку, и
без проверки дефект доживает до продакшена. Делить на 32768.

Также отклоняются: NaN/Inf в сэмплах, `audio_len` больше переданного буфера,
`audio_len` больше 25 с.

### Ресемплинг с 8 кГц

Телефония даёт 8 кГц. Апсемплинг не добавляет информации, но модель обучена на
16 кГц, и качество ресемплера влияет на WER. Использовать полифазный
(`scipy.signal.resample_poly`), **не** линейную интерполяцию, и **один раз на
сегмент**, а не покадрово — иначе на границах кадров появляются артефакты
фильтра.

```python
from math import gcd
from scipy.signal import resample_poly

g = gcd(8000, 16000)
audio_16k = resample_poly(audio_8k, 16000 // g, 8000 // g).astype(np.float32)
```

## 4. Бакеты: как выбрать модель

Сервис публикует **не одну модель, а по одной на диапазон длительности**.
Причина техническая: Triton привязывает оптимизационный профиль TensorRT к
инстансу, а не выбирает его по форме запроса, поэтому «четыре профиля в одной
модели» не работает, а четыре модели работают.

Клиент дополняет аудио нулями до границы бакета и вызывает модель этого бакета.
Тот же паддинг — условие, при котором Triton вообще может батчить запросы: он
группирует только одинаковые формы.

Карта лежит в `model_repository/manifest.json` внутри контейнера
(`docker cp gigaam-triton:/models/manifest.json .`):

```json
{
  "variant": "v3_e2e_ctc",
  "vocab_size": 256,
  "num_classes": 257,
  "blank_id": 256,
  "ensembles": [
    {"name": "gigaam_v3_e2e_ctc_2s",  "bucket_s": 2.0,  "pad_to_samples": 32000},
    {"name": "gigaam_v3_e2e_ctc_5s",  "bucket_s": 5.0,  "pad_to_samples": 80000},
    {"name": "gigaam_v3_e2e_ctc_10s", "bucket_s": 10.0, "pad_to_samples": 160000},
    {"name": "gigaam_v3_e2e_ctc_20s", "bucket_s": 20.0, "pad_to_samples": 320000}
  ]
}
```

Правило выбора: **наименьший бакет, в который помещается сегмент.** Читать
манифест, а не хардкодить имена: набор бакетов конфигурируется при сборке.

### Паддинг не обязателен

Вход `audio` объявлен переменной длины, а истинная длина передаётся отдельно в
`audio_len`, поэтому **можно слать только полезную часть**. Проверено: одно и то
же аудио с паддингом и без даёт логпробы, совпадающие побитово (max разница
0.000e+00), и одинаковый текст.

Паддинг нужен ровно для одного — чтобы Triton мог склеивать запросы в батч: он
группирует только совпадающие формы. Размен такой:

| | трафик | батчинг |
|---|---|---|
| клиент паддит до бакета | больше | работает |
| клиент шлёт как есть | меньше | не работает |

Через быструю локальную сеть выгоднее паддить. Если сервис отделён от клиента
каналом с заметной задержкой, выгоднее не паддить: на двухсекундной реплике в
трёхсекундном бакете это 125 КБ против 187.

Сегменты длиннее самого большого бакета сервис не принимает. Разбиение — забота
клиента; резать по паузам, а не по таймеру.

## 5. Контракт вызова

Единый для всех вариантов и рантаймов: провайдер не должен знать, что внутри
TensorRT или ONNX, CTC или RNNT.

### Входы

| Имя | Тип | Форма | Комментарий |
|---|---|---|---|
| `audio` | FP32 | `[1, N]` | `N` = длина сегмента либо размер бакета, паддинг необязателен (§4) |
| `audio_len` | INT32 | `[1, 1]` | **истинная** длина до паддинга, в сэмплах |

### Выходы

| Имя | Тип | Форма | CTC | RNNT |
|---|---|---|---|---|
| `text` | BYTES | `[1, 1]` | ✅ | ✅ |
| `tokens` | INT32 | `[1, N]` | ✅ | ✅ |
| `token_scores` | FP32 | `[1, N]` | ✅ | ✅ |
| `tokens_len` | INT32 | `[1, 1]` | ✅ | ✅ |
| `logprobs` | FP32 | `[1, кадры, num_classes]` | ✅ | ✗ |
| `logprobs_len` | INT32 | `[1, 1]` | ✅ | ✗ |

`tokens` и `token_scores` **дополнены до числа кадров**; значимы первые
`tokens_len` элементов. Это добавка к исходной спеке: в батче формы ответов
должны совпадать, а счётчика в ней предусмотрено не было.

`token_scores` — логарифмическая вероятность в кадре, где токен был выпущен.
Уверенность по сегменту разумно считать как среднее: `exp(mean(token_scores))`.

`logprobs` — log-softmax по кадрам, ширина `num_classes` = `vocab_size + 1`,
blank на индексе `blank_id`. Отдаются, чтобы клиент мог декодировать сам —
получить пословную уверенность и тайминги без второго прохода. **Запрашивайте
только нужные выходы**: `logprobs` для 20-секундного бакета это ~2 МБ на запрос.
На GPU их запрос стоит около 2.6 мс к p50; на CPU-профиле — заметно дороже.

У RNNT `logprobs` нет намеренно: транспьюсерная решётка клиенту бесполезна,
уверенность считается по `token_scores`.

### Пример (Python, gRPC)

```python
import json, numpy as np, tritonclient.grpc as grpcclient

client = grpcclient.InferenceServerClient(url="localhost:18001")
manifest = json.load(open("manifest.json"))
buckets = sorted(manifest["ensembles"], key=lambda e: e["pad_to_samples"])

def transcribe(audio_16k: np.ndarray) -> str:
    entry = next(b for b in buckets if audio_16k.size <= b["pad_to_samples"])
    padded = np.zeros(entry["pad_to_samples"], dtype=np.float32)
    padded[: audio_16k.size] = np.clip(audio_16k, -1.0, 1.0)

    a = grpcclient.InferInput("audio", [1, padded.size], "FP32")
    a.set_data_from_numpy(padded[None, :])
    n = grpcclient.InferInput("audio_len", [1, 1], "INT32")
    n.set_data_from_numpy(np.array([[audio_16k.size]], dtype=np.int32))

    out = client.infer(entry["name"], [a, n],
                       outputs=[grpcclient.InferRequestedOutput("text")])
    return out.as_numpy("text")[0][0].decode("utf-8")
```

### Декодирование логпробов на стороне клиента

```python
argmax = logprobs[:logprobs_len].argmax(-1)
keep = argmax != manifest["blank_id"]
keep[1:] &= argmax[1:] != argmax[:-1]      # схлопнуть повторы
tokens = argmax[keep]
```

Результат обязан совпасть с выходом `tokens` сервера — если разошлось, ваша
уверенность и тайминги описывают транскрипт, которого никто не выдавал. Эта
проверка встроена в `scripts/smoke_test.py`.

Токенизатор — SentencePiece, файл лежит в контейнере рядом с моделью
(`/models/ctc_postprocessing/1/<variant>_tokenizer.model`).

## 6. Приоритеты

У очереди два уровня. Уровень 1 (дефолт) — финальные запросы, уровень 2 —
спекулятивные и частичные. Финальный запрос не должен ждать за частичным.

```python
out = client.infer(model, inputs, priority=2)   # спекулятивный
```

## 7. Обязательный прогрев после деплоя

`model_warmup` в Triton прогревает энкодер, но **ensemble прогревать не умеет**,
а у каждого из них есть своя одноразовая стоимость первого запроса (замерено
16–20 мс, и до ~70 мс у первого затронутого в процессе). Плюс первое обращение
на свежем gRPC-канале платит за установление соединения.

Поэтому после старта — по одному холостому запросу на каждый бакет. Это делает
`scripts/smoke_test.py`; если он не подходит, повторите в своём деплой-скрипте.
Без этого первый боевой звонок дня заплатит за прогрев.

## 8. Что ожидать по скорости

Замерено на **staging**-машине RTX PRO 5000 Blackwell, у которой часть GPU была
занята посторонним vLLM-сервером. Прод (RTX PRO 6000) будет быстрее. Читать как
нижнюю границу.

`v3_e2e_ctc`, TensorRT fp16, p99 в мс:

| Аудио / конкурентность | 1 | 8 | 50 |
|---|---|---|---|
| 0.5 с | 23.6 | 48.0 | 48.8 |
| 3 с | 25.8 | 64.0 | 77.1 |
| 15 с | 52.5 | 119.9 | 466.7 |

Пропускная способность — до 1477 запросов/с и RTFx 4353 на коротких репликах.
VRAM ≈ 1 ГБ на инстанс энкодера.

**Задержка определяется размером бакета, а не длиной речи в нём.** Весь конвейер
обрабатывает буфер целиком, реальная длина влияет только на маскирование внутри
энкодера. Замерено на двух секундах речи в разных бакетах:

| паддинг | p50 | p99 |
|---|---|---|
| 3 с | 20.7 | 23.8 |
| 5 с | 25.3 | 28.5 |
| 20 с | 40.7 | 48.7 |

Прямая по этим точкам: **~17 мс фиксировано плюс ~1.2 мс на каждую секунду
буфера**. Поэтому 0.3 с речи в трёхсекундном бакете стоят столько же, сколько
3 с речи в нём же — разница около двух миллисекунд.

**Качество от размера бакета не зависит.** Внутри одного движка паддинг не
меняет результат вообще. Между движками разных бакетов есть расхождения на
уровне выбора fp16-ядер в TensorRT: средняя разница логпробов 0.011 при размахе
значений 44, argmax разошёлся на 1 кадре из 50 и текст остался тем же. Это
довод в пользу небольшого числа бакетов, но не повод бояться за точность.

### Разместите сервис рядом с клиентом

Компьют занимает 20 мс. Полезная нагрузка на одну реплику — сотни килобайт
(двухсекундный сегмент в трёхсекундном бакете это 187 КБ FP32). Через канал
с ограниченной пропускной способностью время передачи легко превышает время
вычисления на порядок: замеренный случай через интернет давал 600 мс на круг
при 33 мс по внутреннему учёту Triton.

Сервис занимает менее гигабайта видеопамяти и один инстанс — отдельной машины
он не требует. Если круг оказался в сотнях миллисекунд, сравните свой таймер с
`success.ns / success.count` из `curl localhost:18000/v2/models/stats`:
расхождение и есть время вне Triton.

`v3_e2e_rnnt` медленнее по p99 в 1.15–1.28 раза на коротких репликах и в
2.7–4.0 раза на пятнадцатисекундных: цикл транспьюсера линеен по кадрам, тогда
как энкодер батчится.

CPU-профиль в 8–20 раз медленнее GPU (RTFx около 3 на коротких репликах) и в
реальном времени не работает. Оговорка: машина, на которой это мерилось, без
AVX-512; на целевом CPU цифры будут другие.

## 9. Качество

Модель `v3_e2e_ctc` совпадает с torch-референсом с CER 0.0000 на golden-наборе,
то есть экспорт и рантайм ничего не теряют относительно исходной модели.

Отдельный вопрос — качество самой модели на ваших данных. Черновой прогон на 11
файлах показал WER 0.220 против 0.096 у сравниваемой системы, **но этот результат
не следует принимать за оценку**: у четверти файлов эталон был дословно снят с
выхода конкурента, а длинные записи GigaAM получал уже нарезанными. Детали и
разбивка — `PREP.md` §6f. Мерить надо на своём корпусе с независимой разметкой.

Практическое следствие для интеграции: **у `v3_e2e_*` целевая форма текста иная**
— cased, с пунктуацией, числа цифрами. Если вы сравниваете с системой, которая
отдаёт lowercase без пунктуации, приводите обе стороны к одной форме, иначе
«двадцать пять» против «25» даст две ошибки на ровном месте. Готовый
нормализатор — `eval/normalize.py`.

## 10. Диагностика

| Симптом | Причина |
|---|---|
| Ошибка `audio peak amplitude ...` | int16-сэмплы без деления на 32768 (§3) |
| Ошибка `audio_len ... outside the supplied audio` | несогласованные `audio` и `audio_len` |
| Ошибка `exceeds max_audio_s` | сегмент длиннее 25 с, нужен VAD (§4) |
| `... exceeds the largest bucket` | сегмент длиннее самого большого бакета |
| Старт длится десятки минут | собирается TRT-движок; том `/cache` не сохранился |
| Первый запрос в разы медленнее | не сделан прогрев ensemble (§7) |
| Пустой текст без ошибки | не должно случаться; если случилось — это баг сервиса |

Метрики Triton на `:18002/metrics`: очередь, время вычисления и счётчики по
каждой модели ensemble отдельно, что позволяет увидеть, где именно уходит время.
