# Спецификация: `gigaam-triton` — сборка и эксплуатация инференс-сервера GigaAM v3

Версия: 0.1 · Дата: 2026-08-06 · Статус: к реализации

---

## 1. Цель

Собрать воспроизводимый Docker-образ Triton Inference Server, обслуживающий модели
GigaAM v3 (CTC и RNNT) с рантаймами TensorRT (GPU) и ONNX Runtime (GPU/CPU),
максимально оптимизированный под Blackwell SM120, плюс eval-модуль для
честного сравнения с текущим продакшн-деплоем T-one на Triton.

Работу выполняет агент на сервере с GPU, поэтому **каждый нетривиальный выбор
проверяется замером, а не рассуждением**. Спека задаёт, что мерить и какие
цифры считать приемлемыми.

### 1.1. Что входит в объём

- Скрипт сборки образа с параметризацией по варианту модели, рантайму и точности.
- Генератор Triton model repository (`config.pbtxt` + артефакты).
- Конвертация PyTorch → ONNX → TensorRT с кэшем движков.
- Smoke-тесты и перф-профилирование внутри контейнера.
- Eval: WER/CER/латентность GigaAM vs T-one на общем корпусе.

### 1.2. Что НЕ входит

- Интеграция в SecondChain — отдельная спека (`secondchain-gigaam-provider-spec.md`).
- Дообучение моделей.
- Стриминговый режим — GigaAM офлайновая, см. §11.1.

## 4. Выбор базового образа: критично для Blackwell

**Инструкция из апстрима не подходит.** Официальный `triton_scripts/README.md`
предписывает конвертировать TRT в контейнере `nvcr.io/nvidia/tensorrt:24.10-py3`.
Этот TensorRT предшествует поддержке SM120 — на RTX PRO 6000 сборка движка либо
упадёт, либо соберётся в JIT-режиме с деградацией. Хардкодить версию **запрещено**.

### 4.1. Требование к `detect_env.py`

Скрипт обязан:

1. Прочитать `nvidia-smi --query-gpu=name,compute_cap,driver_version --format=csv`.
2. Перебрать список кандидатных образов Triton (свежие сначала), для каждого
   выполнить `docker run --rm --gpus all <image> bash -c "trtexec --version; nvcc --version"`.
3. Выбрать первый образ, у которого:
   - TensorRT собирает тестовый движок под обнаруженный compute capability
     (проверка: минимальный ONNX с одним Conv, `trtexec --fp16 --onnx=... --saveEngine=/tmp/t.plan`);
   - CUDA runtime ≥ требуемого драйвером.
4. Записать выбор в `cache/env.json` вместе с полными версиями и хэшем проверки.
5. При провале всех кандидатов — упасть с внятным сообщением, перечислив, что
   именно проверялось. Не откатываться молча на CPU.

Тот же образ используется и для сборки движка, и для рантайма — иначе версия
TRT в движке разойдётся с версией в сервере, и Triton откажется грузить `.plan`.

### 4.2. Двухстадийная сборка

- `Dockerfile.builder`: базовый Triton-образ + `torch`, `gigaam`, `onnx`,
  `onnxruntime-gpu`, `polygraphy`. Тяжёлый, наружу не уезжает.
- `Dockerfile.runtime`: тот же базовый образ + `onnxruntime-gpu` (нужен для
  Python-бэкенда RNNT) + пакет `gigaam` (Python-модели делают `import gigaam`)
  + сгенерированный model repository. Без torch.

## 5. Этап 1 — экспорт в ONNX

`scripts/export_onnx.py --variant <v3_e2e_ctc|...> --dtype fp16|fp32 --out <dir>`

Реализация поверх `gigaam.load_model(...).to_onnx(...)`. Требования:

1. **fp16 для GPU-таргетов, fp32 для CPU-таргетов.** Апстрим по умолчанию
   экспортирует fp32; для GPU это лишний расход VRAM и скорости.
2. **Фиксация препроцессинга.** У v3 препроцессинг отличается от v2, а
   апстримовый конвертер пишет конфиг препроцессинга в общую директорию —
   он определяется последней сконвертированной моделью. Скрипт обязан:
   - писать конфиг препроцессинга в `preprocessing/<family>/`, где
     `family ∈ {v2, v3}`;
   - при конвертации второго варианта той же семьи сверять sha256 конфига
     с уже записанным и падать при расхождении;
   - **запрещать** попадание v2- и v3-моделей в один model repository
     (проверка в `gen_model_repo.py`, не только тут).
3. Сохранять рядом `vocab.txt`/`tokens.txt` и метаданные варианта
   (`variant`, `subsampling_factor`, `frame_ms=40`, `sample_rate=16000`,
   `max_audio_s=25`, `output_case`, `has_punctuation`) в `meta.json`.
   Эти метаданные потребляет провайдер SecondChain — не выдумывать их там.
4. Валидация экспорта: прогнать `testdata/golden/*.wav` через torch и через
   ONNX, сравнить транскрипты. Расхождение допустимо только в пределах
   CER ≤ 0.5%, иначе падать.

## 6. Этап 2 — сборка TensorRT

`scripts/build_trt.py --onnx <path> --precision fp16|bf16|fp32 --buckets 2,5,10,20 --out <path>`

### 6.1. Профили оптимизации и бакеты

Динамическая ось — длина аудио. Вместо одного профиля с широким диапазоном
собирать **несколько оптимизационных профилей**, по одному на бакет длительности:

| Бакет | min | opt | max |
|---|---|---|---|
| 2 s | 0.3 s | 1.5 s | 2 s |
| 5 s | 2 s | 3.5 s | 5 s |
| 10 s | 5 s | 7 s | 10 s |
| 20 s | 10 s | 14 s | 20 s |

Обоснование: клиент паддит вход до ближайшего бакета (см. спеку провайдера),
и это же условие делает возможным dynamic batching на сервере — Triton
батчит только запросы одинаковой формы. Один широкий профиль даёт заметно
худший kernel selection на коротких репликах, а короткие реплики — наш
основной трафик.

Набор бакетов параметризуется; дефолт выше подобран под телефонный диалог.

### 6.2. Флаги сборки

Обязательные:
- `--fp16` (или `--bf16`, замерить оба — на Blackwell bf16 иногда стабильнее
  по точности при той же скорости);
- `--builderOptimizationLevel=5`;
- `--timingCacheFile=cache/trt_timing.cache` — переиспользовать между сборками;
- `--memPoolSize=workspace:8192` (тюнить по факту).

Проверить замером, включать по результату:
- `--stronglyTyped` — если экспорт уже в fp16, убирает неявные касты;
- `--useCudaGraph` (в `trtexec` только для профилирования; в Triton
  эквивалент — `optimization { cuda { graphs: true } }`);
- sparsity — почти наверняка бесполезна для Conformer, но проверить дёшево.

### 6.3. Кэш движков

Движок TRT привязан к железу и версиям. Ключ кэша:

```
sha256(onnx_sha256 + trt_version + gpu_name + compute_cap + driver_version + flags_json)
```

Правила:
- Движки **не запекаются в образ**. Образ содержит ONNX + скрипты; движок
  собирается при первом запуске на целевой машине и кладётся в примонтированный
  `cache/`. Иначе образ невоспроизводим и ломается при апдейте драйвера.
- При старте контейнера entrypoint проверяет ключ; при несовпадении —
  пересборка с логом причины.
- Сборка 4 бакетов Conformer'а занимает минуты — прогревать при деплое,
  а не на первом звонке.

## 7. Model repository

### 7.1. Layout

```
model_repo/
├── preprocessing/          # python backend: wav → log-mel
├── gigaam_ctc_encoder/     # trt или onnx
├── ctc_postprocessing/     # python: greedy decode → text
├── gigaam_rnnt_encoder/    # trt или onnx
├── rnnt_decoder_joint/     # python + onnxruntime: transducer loop
└── gigaam_<variant>/       # ensemble
```

### 7.2. Контракт ensemble — расширенный против апстрима

Апстримовый ensemble отдаёт только текст. Нам этого мало.

**Входы:**

| Имя | Тип | Форма | Комментарий |
|---|---|---|---|
| `audio` | FP32 | `[-1]` | 16 kHz mono, диапазон `[-1, 1]` |
| `audio_len` | INT32 | `[1]` | реальная длина без паддинга |

**Выходы:**

| Имя | Тип | Комментарий |
|---|---|---|
| `text` | BYTES | итоговый транскрипт |
| `logprobs` | FP32 `[-1, V]` | лог-softmax по фреймам (**только CTC**) |
| `logprobs_len` | INT32 | число валидных фреймов |
| `tokens` | INT32 `[-1]` | id токенов |
| `token_scores` | FP32 `[-1]` | скор на токен |

`logprobs` — обязательное требование: провайдер SecondChain декодирует CTC
на своей стороне, чтобы получить confidence и word-level тайминги без второго
прохода. Клиент запрашивает подмножество выходов через `outputs=[...]`.

Для RNNT `logprobs` не выдаём (транспьюсерный латтис бесполезен клиенту) —
отдаём `tokens` + `token_scores`, confidence считается как среднее по токенам.

**Требование:** входной контракт (`audio` в float32 16 kHz) одинаков для всех
вариантов и рантаймов. Провайдер не должен знать, что внутри.

### 7.3. `config.pbtxt` — обязательные секции

Для энкодера (TRT/ONNX GPU):

```
max_batch_size: 8
dynamic_batching {
  preferred_batch_size: [2, 4, 8]
  max_queue_delay_microseconds: 1000
  priority_levels: 2
  default_priority_level: 1
}
instance_group [{ count: 2, kind: KIND_GPU }]
optimization { cuda { graphs: true } }
response_cache { enable: false }
model_warmup [{
  name: "warmup_2s"
  batch_size: 1
  inputs { ... zero audio 2s ... }
  count: 3
}]
```

Замечания:
- `max_queue_delay_microseconds: 1000` — потолок добавленной латентности 1 мс.
  Не ставить десятки миллисекунд «ради throughput»: у нас реалтайм.
- `priority_levels: 2` — уровень 2 для спекулятивных/партиальных запросов
  провайдера, уровень 1 (дефолт) для финальных. Финальные не должны стоять
  в очереди за партиалами.
- `model_warmup` обязателен: первые 2–3 вызова ONNX Runtime в 3–5 раз медленнее
  холодного старта, а CUDA-графы нужно захватить до первого боевого запроса.
- `count: 2` — стартовое значение, подобрать по §9.

Для CPU-профиля:

```
instance_group [{ count: N, kind: KIND_CPU }]
parameters {
  key: "intra_op_thread_count" value: { string_value: "4" }
}
parameters {
  key: "inter_op_thread_count" value: { string_value: "1" }
}
```

`N × intra_op ≈ число физических ядер`. Мерить обе крайности: много инстансов
по 1 потоку против одного инстанса на все ядра — для Conformer на CPU
обычно выигрывает первое при конкурентной нагрузке.

### 7.4. RNNT: главный риск производительности

В апстримовой схеме энкодер идёт в ONNX/TRT, а decoder/joint крутятся в
Python-бэкенде на onnxruntime. Это боттлнек: по официальному бенчмарку на CUDA
CTC даёт 0.034 с против 0.403 с у e2e_rnnt — разница на порядок, и она вся
в цикле транспьюсера, а не в энкодере.

Требования к реализации `rnnt_decoder_joint`:

1. Преаллокация всех буферов на старте, `onnxruntime.IOBinding`, никаких
   аллокаций внутри цикла.
2. Состояние декодера держать на устройстве (`OrtValue` на CUDA), не гонять
   через хост на каждом шаге.
3. Ограничить `max_symbols_per_frame` (значение по умолчанию для char-словаря
   слишком щедрое и даёт лишние итерации).
4. Флаг `--rnnt-decoder python|trt-loop`: второй вариант — decoder и joint
   тоже в TRT, цикл драйвится в Python поверх device-резидентных тензоров.
   Реализовать после того, как замерен первый.
5. Обязательно замерить и отчитаться: доля времени энкодер / joint / оверхед
   Python-бэкенда.

**Решение по умолчанию:** если после оптимизации RNNT остаётся хуже CTC более
чем в 4 раза по p99 — в прод идёт `v3_e2e_ctc`, RNNT остаётся как
офлайн-движок для постобработки записей. Не тратить на него больше двух дней.

## 8. CLI сборки

```bash
./build.sh \
  --variant v3_e2e_ctc,v3_ctc \
  --runtime trt \
  --precision fp16 \
  --buckets 2,5,10,20 \
  --max-batch-size 8 \
  --instances 2 \
  --image gigaam-triton:0.1 \
  --model-repo ./model_repo \
  --cache ./cache
```

| Флаг | Значения | Дефолт |
|---|---|---|
| `--variant` | список из §2.1 | `v3_e2e_ctc` |
| `--runtime` | `trt`, `onnx-gpu`, `onnx-cpu` | `trt` |
| `--precision` | `fp16`, `bf16`, `fp32`, `int8` | `fp16` (GPU), `int8` (CPU) |
| `--buckets` | секунды через запятую | `2,5,10,20` |
| `--skip-trt` | — | собрать только ONNX-репозиторий |
| `--verify` | — | прогнать golden-тесты после сборки |

Скрипт идемпотентен: повторный запуск с теми же аргументами не пересобирает
ничего, что уже лежит в кэше с валидным ключом.

`int8` для CPU: динамическая квантизация ONNX Runtime. По публичным замерам
у v3 int8 почти бесплатен (RTFx 58.8 → 52.2 у CTC, у RNNT вовсе без потерь),
в отличие от v2, где int8 обваливал скорость втрое. Проверить на своём железе
и обязательно замерить WER до/после — скорость без WER здесь ничего не значит.

## 9. Профилирование и приёмочные замеры

`scripts/perf_profile.py` гоняет `perf_analyzer` и складывает результат в
`cache/perf/<variant>_<runtime>_<precision>.json`.

### 9.1. Обязательная матрица замеров

- Конкурентность: 1, 4, 8, 16, 32, 50.
- Длительности: 0.5 s, 1 s, 3 s, 8 s, 15 s.
- Метрики: p50/p95/p99 end-to-end по gRPC, throughput (запросов/с), RTFx,
  VRAM на инстанс, загрузка GPU.
- Отдельно: холодный первый запрос против прогретого (доказать, что
  `model_warmup` отработал).

### 9.2. Приёмочные критерии

| Критерий | Порог |
|---|---|
| `v3_e2e_ctc` / TRT fp16, 3 с аудио, конкурентность 1 | p50 ≤ 25 мс |
| То же, конкурентность 50 | p99 ≤ 60 мс |
| VRAM на инстанс энкодера | ≤ 2 GB |
| Golden-тесты (CER против torch-референса) | ≤ 0.5% |
| Пустых выходов на корпусе коротких реплик | ≤ 1% |
| Холодный старт до готовности | ≤ 90 с включая сборку движка из кэша |

Для RNNT пороги не задаём — фиксируем фактические цифры и принимаем решение
по §7.4.

## 10. Eval-модуль

### 10.1. Назначение

Ответить на один вопрос: **на наших звонках GigaAM v3 лучше или хуже
текущего T-one, и на сколько.** Публичные таблицы обеих команд получены на
внутренних данных и друг другу противоречат — доверять им нельзя.

### 10.2. Формат корпуса

`manifest.jsonl`, по строке на сегмент:

```json
{"audio": "calls/2026-07/abc.wav", "ref": "да конечно записывайте",
 "duration": 1.24, "subset": "short", "domain": "hr", "channel": "caller",
 "sr": 8000}
```

Обязательные срезы (`subset`):
- `short` — реплики ≤ 1.5 с (да/нет/угу/алло/имена). **Главный срез**:
  именно на нём в прошлом ломались кандидаты.
- `normal` — 1.5–8 с.
- `long` — 8–20 с.
- `noisy` — плохой канал, фон, перебивания.
- `entities` — имена, адреса, номера, суммы.

### 10.3. Нормализация текста — самая частая ошибка в таких сравнениях

T-one отдаёт lowercase без пунктуации. `v3_e2e_*` отдаёт cased текст с
пунктуацией и **числами в цифровой записи**. Сравнивать их напрямую по WER
бессмысленно: «двадцать пять» против «25» даст две ошибки на пустом месте.

`normalize.py` приводит обе стороны к единой форме:

1. lowercase;
2. `ё` → `е`;
3. удаление пунктуации, схлопывание пробелов;
4. **цифры → слова** (`num2words` ru) — приводим к устной форме, а не наоборот,
   потому что обратная ITN неоднозначна;
5. единый формат для латиницы и аббревиатур (правила задать явно и
   зафиксировать в тестах);
6. удаление хезитаций (`э`, `мм`) — опционально, считать метрику в двух вариантах.

Нормализатор покрывается юнит-тестами с ~30 кейсами из реальных расшифровок.
Отчёт обязан содержать WER **и** в сыром виде, и после нормализации — если
разрыв велик, это сигнал, что что-то в нормализации не так.

Для честного сравнения акустики использовать пару `v3_ctc` (lowercase) vs
T-one; `v3_e2e_ctc` сравнивать дополнительно, отмечая, что у него другой
таргет.

### 10.4. Движки

`eval/engines/tone_triton.py` — обёртка над **официальным клиентом из репозитория
T-one**, а не переписанная логика. Причина: у T-one декодирование (splitter +
CTC decoder, при `beam_search` — с KenLM) идёт на клиенте, и любая самодельная
реализация исказит его качество. Поддержать оба декодера (`greedy`, `beam_search`)
и мерить их отдельно — в проде используется `beam_search`, и сравниваться нужно
именно с ним.

`eval/engines/gigaam_triton.py` — тонкий клиент к нашему ensemble.

Дополнительно `gigaam_local_onnx` (через `onnx-asr`) как sanity-check: если
цифры Triton-движка расходятся с локальным ONNX больше чем на 0.5% CER,
значит сломан препроцессинг или паддинг в ensemble.

### 10.5. Протокол коротких реплик

Для среза `short` прогон делается сеткой по контексту:

- pre-roll: 0 / 150 / 300 / 500 мс
- hangover (хвост): 0 / 150 / 300 / 500 мс

Результат — таблица «точность против длины контекста». Победившая пара
значений уезжает дефолтом в конфиг провайдера SecondChain. Это дешёвый
эксперимент с прямым влиянием на продакшн-качество.

### 10.6. Метрики и отчёт

- WER, CER — общий и по каждому срезу.
- Sentence accuracy (доля точных совпадений) — для `short` информативнее WER.
- Empty output rate.
- Латентность: p50/p95/p99, RTFx.
- Матрица подстановок топ-50 — что именно путается.

Выход: `results.json` (машиночитаемый), `report.md` (таблицы + выводы),
`errors.csv` (худшие 200 сегментов с ref/hyp для ручного просмотра).

## 11. Известные грабли

### 11.1. GigaAM офлайновая

Модель не потоковая: энкодер полноконтекстный, состояния между вызовами нет,
`.transcribe` рассчитан на аудио до 25 с. Кормить её чанками по 300 мс, как
T-one, нельзя — это архитектурное ограничение, а не настройка. Из этого
следуют требования к паддингу, бакетам и к дизайну провайдера.

### 11.2. Тихие отказы на неверном входе

При подаче int16 вместо float32 модель возвращает пустую строку без ошибки и
предупреждения. Провайдер и ensemble обязаны валидировать dtype и диапазон на
входе и падать явно.

### 11.3. Коллизия препроцессинга

См. §5.2 — общий препроцессинг в ensemble определяется последней
сконвертированной моделью. Смешивание семейств v2/v3 в одном репозитории
запрещено проверкой.

### 11.4. Инвалидация движков

Апдейт драйвера или образа Triton делает `.plan` нерабочим. Ключ кэша это
ловит, но деплой-процедура должна закладывать время на пересборку.

### 11.5. Ресемплинг 8 → 16 кГц

Телефония даёт 8 кГц. Апсемплинг в 16 кГц не добавляет информации, но модель
обучена на 16 кГц, и качество апсемплера влияет на WER. Использовать
`scipy.signal.resample_poly` (polyphase), не линейную интерполяцию. Ресемплить
**один раз на сегмент**, не по 20-мс фреймам — иначе на границах фреймов
появятся артефакты фильтра.
