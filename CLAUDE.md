This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Состояние репозитория

Корень git-репозитория — этот каталог (`github.com/usunrise88/gigaam-triton`).

- `gigaam-triton-spec.md` — спецификация (v0.1). **Источник истины.** Читать
  целиком перед любой работой: почти каждое требование обосновано конкретной
  граблей, а не вкусом. Порядок работ — §12, промежуточные отчёты после шагов 4, 6, 7.
- `PREP.md` — **отчёт подготовки: читать сразу после спеки.**
  Фиксирует реальное окружение, выбранный базовый образ с доказательством,
  расхождения апстрима со спекой и принятые решения.
- `cache/env.json` — машиночитаемый результат детекта окружения.
  `detect_env.py` должен его воспроизводить и владеть им.
- `../_ref/` (вне репозитория) — клоны для чтения: `GigaAM` (HEAD 559d88d), `T-one`, проба SM120,
  артефакты T-one (`model.onnx`, `kenlm.bin`). Не редактировать, это апстрим.

## Уже установленные факты (не перепроверять с нуля)

- **Базовый образ на staging: `nvcr.io/nvidia/tritonserver:25.06-py3`** — TRT 10.11, CUDA 12.9,
  Triton 2.59.0, py3.12, `trtexec` в `/usr/src/tensorrt/bin/`. Проба сборки fp16
  под SM120 пройдена. На нём же работают прод-T-one и его официальная инструкция.
- **Прод (RTX PRO 6000 Blackwell 96 GB, драйвер 595.91.07): `tritonserver:26.08-py3`** —
  TRT 11.2.1, CUDA 13.4 (контейнер в режиме CUDA forward compatibility), Triton 2.72.0.
  Причина — безопасность: сервис опубликован без авторизации, а Triton < 26.07 имеет
  сетевые CVE без авторизации (см. README §9). TRT 11 строго типизирован: `--fp16` нет,
  точность движка = dtype ONNX (`build_trt.py` это проверяет).
- **Эталоны `<имя>_<N>s`** — ровно первые N секунд `<имя>.wav`, нарезаются в `smoke_test.py`;
  тексты `example_3s`/`example_5s` пересняты torch-моделью на таких клипах.
- Машина — **staging**: RTX PRO 5000 Blackwell 48 GB, SM120, драйвер 580.119.02.
  GPU делится с `vllm-qwen35-moe` (27 GB VRAM). Замеры идут **без остановки vLLM**
  по решению владельца — значит, трактовать их как нижнюю границу и помечать
  фактической загрузкой GPU.
- Веса всех четырёх вариантов лежат в `~/.cache/gigaam`, MD5 сверены.
- Прод-T-one жив на портах **17000/17001/17002** — наш Triton поднимать на
  **18000/18001/18002**.
- `SecondChain/venv` (py3.10) уже содержит `tone`, `tritonclient`, `onnxruntime`,
  `scipy` — годится для eval. torch там нет и не нужен: экспорт живёт в builder-образе.

## Ловушки (проверены на практике, не по чтению)

- **Не брать за основу `triton_scripts/run_convert_onnx.py`**: он подменяет forward
  так, что CTC отдаёт `token_ids = argmax`, а не логпробы. Это ломает контракт §7.2.
  Наш `export_onnx.py` отдаёт и то, и другое: логпробы провайдеру, argmax считается
  на GPU внутри графа, чтобы Python-бэкенд не таскал `[T, V]` через хост.
- **У v3 препроцессинг не на дефолтах библиотеки**: `n_fft=320`, `center=False`
  (у v2 — 400 с центрированием). Формула кадров, соответственно,
  `(samples - win) // hop + 1`, а не `samples // hop + 1`. Все счётчики кадров
  (шейпы TRT-профилей, warmup, паддинг бакетов) берутся из `meta.json`, а не
  предполагаются: ошибка на два кадра выкидывает запрос за границу профиля.
- **CTC-голова на один класс шире токенизатора**: 256 токенов, 257 классов,
  blank на индексе 256. `vocab_size` и `num_classes` — разные поля; объявишь
  тензор шириной 256 — Triton не загрузит модель.
- **`ffmpeg` — необъявленная зависимость** `gigaam.preprocess.load_audio`. В базовом
  образе его нет, как и `soundfile`. Ставить в оба Dockerfile.
- **Triton не выбирает optimization profile по форме запроса** — профиль
  прибивается к `instance_group`. Отсюда «ensemble на бакет»: четыре профиля в
  одной модели не работают, четыре модели работают.
- **`np.savez` пишет zip с таймстампами.** Сравнивать препроцессинг между
  вариантами по sha256 файла нельзя — только по содержимому массивов.
- Имена входов/выходов ONNX различаются между CTC и RNNT (`features`/`feature_lengths`
  против `audio_signal`/`length`) — параметризовать в шаблонах, не хардкодить.
- `MAX_LETTERS_PER_FRAME = 3` — модульная константа в `gigaam/onnx_utils.py`;
  §7.4.3 требует сделать её настраиваемой.

## Дефолты, поставленные по замеру (не менять без нового замера)

- `OMP_NUM_THREADS=1` и соседи в runtime-образе — пул потоков numpy на массивах
  499×320 дороже самой работы: препроцессинг 28.6 → 8.5 мс.
- CUDA-графы **выключены**: разницы нет, а захват падает на части инстансов.
- Провайдер RNNT-цикла — **`cpu`**: 127 мс против 198 мс на CUDA. Декодер — LSTM
  шириной 320, launch + синхронизация на шаг дороже арифметики.
- `reduce_range` в квантизации следует наличию VNNI. На этой машине его нет
  (виртуальный Broadwell, только AVX2), и `reduce_range=False` давал насыщение
  аккумулятора: WER 0.0385 вместо 0.0000.
- Эталонные транскрипты — **по варианту** (`example.v3_e2e_ctc.txt`): CTC и RNNT
  расставляют пунктуацию по-разному, и общий эталон валит smoke не по делу.

## Про сравнения с эталоном

Гейт `check_logmel.py` сначала сравнивал numpy-логмел с torch в **float32** и
падал на 3.8e-3. Диагностика показала: это собственный float32-шум torch на бине
с энергией 1.8e-8, а не наша ошибка — против float64-референса replay совпадает
до 2.4e-11. Порог надо ставить по уровню корректной реализации, а не по уровню
шума того, с чем сравниваешь. Ослаблять порог, чтобы «прошло», — здесь ровно тот
случай, когда так делать нельзя.

## Целевая структура и команды

Структура репозитория задана в §3 спеки, CLI сборки — в §8. Ничего из этого пока
не существует; при создании файлов следовать этим разделам буквально, чтобы
пути в спеке оставались валидными.

Планируемая точка входа — `./build.sh` с флагами `--variant`, `--runtime`,
`--precision`, `--buckets`, `--max-batch-size`, `--instances`, `--image`,
`--model-repo`, `--cache`, `--skip-trt`, `--verify`. Скрипт обязан быть
идемпотентным: повтор с теми же аргументами ничего не пересобирает, если в
`cache/` лежит артефакт с валидным ключом.

`model_repo/` и `cache/` генерируются и идут в `.gitignore`.

## Что нужно знать до того, как писать код

**Замер вместо рассуждения.** Работа идёт на машине с GPU; спека прямо требует
проверять каждый нетривиальный выбор замером (`scripts/perf_profile.py` →
`cache/perf/*.json`) и задаёт приёмочные пороги в §9.2. «Должно быть быстрее» —
не аргумент.

**Версию базового образа не хардкодить.** Инструкция апстрима (`tensorrt:24.10-py3`)
предшествует поддержке SM120 и на целевом RTX PRO 6000 Blackwell даёт падение
или JIT-деградацию. Образ выбирает `detect_env.py` перебором кандидатов с
реальной пробной сборкой движка (§4.1). Один и тот же образ используется и для
сборки движка, и для рантайма — иначе Triton не загрузит `.plan`.

**Движки TRT не запекаются в образ.** Ключ кэша включает версию TRT, имя GPU,
compute cap, версию драйвера и флаги (§6.3). Сборка — при первом запуске на
целевой машине, в примонтированный `cache/`.

**Контракт ensemble шире апстримового.** Кроме `text` отдаются `logprobs`
(только CTC — провайдер SecondChain декодирует у себя ради confidence и
word-level таймингов), `logprobs_len`, `tokens`, `token_scores`. Вход —
всегда `audio` FP32 16 kHz + `audio_len` INT32, одинаково для всех вариантов и
рантаймов.

**Тихие отказы.** int16 вместо float32 на входе → пустая строка без ошибки.
Валидировать dtype и диапазон явно, падать громко. То же с препроцессингом:
конфиг v2 и v3 различается и перетирается последней сконвертированной моделью —
писать в `preprocessing/<family>/`, сверять sha256, запрещать смешивание
семейств в одном model repository (проверка и в `export_onnx.py`, и в
`gen_model_repo.py`).

**Латентность важнее throughput.** `max_queue_delay_microseconds: 1000`, не
десятки миллисекунд. `model_warmup` обязателен — первые вызовы ORT в 3–5 раз
медленнее, CUDA-графы нужно захватить до боевого трафика.

**Бакеты длительности связаны с клиентом.** Отдельный оптимизационный профиль
TRT на бакет (2/5/10/20 с) существует не только ради kernel selection: клиент
паддит до ближайшего бакета, и это же делает возможным dynamic batching (Triton
батчит только одинаковые формы).

**RNNT — главный риск.** Боттлнек в транспьюсерном цикле, не в энкодере (по
официальному бенчмарку 0.403 с против 0.034 с у CTC). Требования к реализации —
§7.4. Если после оптимизации RNNT хуже CTC более чем в 4× по p99, в прод идёт
`v3_e2e_ctc`; больше двух дней на RNNT не тратить.

**Eval честный или никакой.** T-one отдаёт lowercase без пунктуации, `v3_e2e_*` —
cased с пунктуацией и цифрами; прямое сравнение WER бессмысленно. `normalize.py`
приводит обе стороны к устной форме (цифры → слова, не наоборот), отчёт содержит
WER и до, и после нормализации. Обёртка над T-one использует **официальный клиент
из его репозитория** (декодирование там на клиенте, самодельная реализация
исказит качество) и меряет `greedy` и `beam_search` раздельно — в проде
`beam_search`. Главный срез — `short` (≤ 1.5 с): именно на нём ломались прошлые
кандидаты.

**Ресемплинг 8 → 16 кГц** — `scipy.signal.resample_poly`, один раз на сегмент,
не по фреймам.
